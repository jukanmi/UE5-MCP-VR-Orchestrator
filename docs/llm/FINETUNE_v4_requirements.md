**작성**: 2026-09-05
**근거**: 파인튜닝 v1/v2/v3 + 베이스 + qwen3:8b 전수 실측
**재현**: `python tools/finetune_eval/stage1_bench.py --models <태그> --seed-history`

## 1. 왜 v4 가 필요한가

v1~v3 중 **8종 의도를 전부 통과한 버전이 없다.** 각 버전이 서로 다른 곳에서 깨지고,
프롬프트 수정으로는 메워지지 않는 지점이 남는다.

측정 조건(전 모델 동일): NPC=Moca, 인벤토리 3종(Rock·Bandage·WaterSkin),
가구 1종(Bed id=1002), 오염된 대화기록 6항목 주입, 질문 8종 × 2회, temperature 0.5.

| 케이스 | 기대 | v1 | v2 | v3 | qwen3:8b |
|---|---|---|---|---|---|
| "돌 좀 줘" | GiveItem/Rock | 액션 0/2 | 2/2 | HandObject | 1/2 |
| "붕대 하나 건네줘" | GiveItem/Bandage | 2/2 | `item='1'` | HandObject 2/2 | 2/2 |
| "빵 좀 줘"(미보유) | 거절, 액션 없음 | 얼버무림 | 명확 | **보유 목록 나열** | **보유 목록 나열** |
| "가방에 뭐 있어?" | 보유 나열 | 문형복사 | 문형복사 | **실제 나열** | 문형복사 + `Scan` |
| "나 따라와" | Follow/Player | 2/2 | 2/2 | 2/2 | 2/2 (대사는 예시 복창) |
| "침대에 누워" | Sleep/1002 | 2/2 | **0/2** | **0/2** | 2/2 |
| "그 돌 좀 보여줘" | HandObject/Rock | 액션 0/2 | 2/2 | 액션 0/2 | 2/2 |
| "큰 소리 나는데 괜찮아?" | 대사만 | 2/2 | `UseItem '1002'`+`Dodge` | 2/2 | `Stop`·`SignalAllies` |
| **ItemID 정확도** | 정확한 id | 2/2 | **`'1'`·`'돌멩이'`·`'1002'`** | 4/4 | 4/4 |

### 버전별 실패 성격

- **v1** — 아이템 액션을 자주 아예 못 낸다("돌 좀 줘"·"돌 보여줘" 0/2). GiveItem 우위는
  "건네줘" 같은 명시적 동사에서만 나타난다. 비아이템 액션(Follow·Sleep)과 액션 절제는 가장 안정적.
- **v2 — 배제 대상.** ItemID 자리에 `'1'`, 표시명 `'돌멩이'`, 심지어 가구 ID `'1002'` 를 넣는다.
  `UseItem item='1002'` 는 런타임에서 조용히 실패한다. 평온한 상황에 `Dodge` 를 쏘기도 했다.
- **v3** — ItemID·인벤토리 인지·액션 절제가 가장 좋다. 유일하게 "가방이요… 붕대랑 돌멩이가
  들어있어요" 로 실제 목록을 말했다. 그러나 **모든 전달 요청에 HandObject** 를 내고 Sleep 을 못 낸다.
- **qwen3:8b(비파인튜닝)** — 아이템 이해는 가장 정확하지만 **페르소나 예시 문장을 토씨 그대로
  복창**하고("천천히 와도 괜찮아요… 여기 앉아서 좀 쉬었다 가요."), 무액션 상황에 `SignalAllies`
  같은 전투 액션을 오발한다.

### 같은 모델도 기록 상태로 뒤집힌다 (v1, 2026-09-05)

위 표는 **오염된 기록을 주입한** 조건이다. 같은 v1 을 **백지 기록**으로 돌리면 결과가 크게 다르다:

| 케이스 | 오염 기록 | 백지 기록 |
|---|---|---|
| "돌 좀 줘" | 액션 0/2 | **GiveItem/Rock** ✅ |
| "붕대 건네줘" | GiveItem 2/2 | **GiveItem/Bandage** ✅ |
| "그 돌 보여줘" | 액션 0/2 | **HandObject/Rock** ✅ |
| "침대에 누워" | 2/2 | Sleep/1002 ✅ |
| "큰 소리" | 2/2 | 액션 없음 ✅ |
| "빵 좀 줘" | 얼버무림 | 얼버무림 ❌ (여전히 약함) |
| "가방에 뭐 있어?" | 문형복사 | "안에 든 것들이 너무 많아서…" ❌ (나열 못 함) |

백지에서 **8종 중 7종 통과**. 남는 약점은 인벤토리 나열·미보유 거절 두 가지뿐이다.

이것이 이 문서에서 가장 중요한 사실이다 — **v1~v3 의 "아이템 액션 실패" 상당수는 모델
결함이 아니라 기록 오염의 결과**다. v4 데이터를 짤 때 이 둘을 구분하지 않으면, 실제로는
없는 문제를 고치려 데이터를 낭비하게 된다.

### 프롬프트로 메워지지 않는 것 (실측)

v3 에 소유권 이전 규칙을 주입해 재측정("줘/건네줘 = GiveItem, 보여줘 = HandObject"):

| | 규칙 전 | 규칙 후 |
|---|---|---|
| "돌 좀 줘" | HandObject | HandObject (변화 없음) |
| "붕대 건네줘" | HandObject 2/2 | GiveItem 1/2 |
| "돌 보여줘" | 액션 0/2 | **HandObject 2/2** |
| ItemID | 4/4 | 6/6 |

"보여줘 → HandObject" 는 잡혔으나 **"줘 → GiveItem" 은 안 잡힌다.** 학습 단계에서 굳은
매핑을 프롬프트가 이기지 못한다. → 데이터로 고쳐야 한다.

## 1-B. 2차 측정 — 수량·거래·전투·장착 (2026-09-05)

조건: 인벤토리 **12종**, 대화기록 **백지**, `valid_targets` 에 다른 NPC(`Elara`) 포함, 2회씩.
1차에서 안 본 축을 본다.

| 케이스 | 기대 | v1 | v3 |
|---|---|---|---|
| "돌 3개만 줘" | GiveItem/Rock **amount=3** | GiveItem, **수량 없음** | HandObject, **수량 없음** |
| "돌 줄테니 빵이랑 바꾸자" | Trade give=Rock get=Bread | 무액션 1/2, `Trade` give만 1/2 | `Trade` give만 2/2 |
| **"적이다! 싸워!"** | mode=Combat, Attack/Enemy | **mode=Social, 무액션.** "적이 아니에요" | mode=Combat ✅, **무액션** |
| "위험해, 도망쳐!" | Flee, mode=Combat | mode=Common, Flee 1/2 | **mode=Combat, Flee 2/2** ✅ |
| "검 장착해" | Equip/KnightSword | ✅ 2/2 | ✅ 2/2 |
| "목마르면 물 마셔" | UseItem/WaterSkin Self | **GiveItem 오분류** / 무액션 | 무액션 / **UseItem ✅** |
| "치유 물약 하나 줘" (12종 중) | GiveItem/HealthPotion | ✅ GiveItem 2/2 | HandObject 2/2 |
| "엘라라한테 붕대 갖다줘" | target=**Elara** | HandObject **target=Elara** ✅ | HandObject **target=Elara** ✅ |

### 새로 드러난 문제 5가지

1. **수량(`amount`)을 아무도 안 낸다.** "3개만" 을 대사로는 받아치면서(v3 #2: "여기 있어요, 3개만요")
   `amount` 필드는 비운다. `GiveItem`/`Drop`/`Trade` 는 수량 파라미터가 있는데 학습 데이터에
   수량 사례가 없는 것으로 보인다. 현재는 전부 1개로 처리된다.

2. **`Trade` 가 반쪽만 나온다.** `give_item_id` 만 채우고 `get_item_id` 를 비운다. 교환은 양방향
   지정이 본질인데 한쪽만 나오면 실질적으로 GiveItem 과 같아진다. 미보유 아이템(빵)을 요구받는
   상황 처리도 없다.

3. **전투 인지가 v1 에서 완전히 실패한다.** "적이다! 싸워!" 에 `mode=Social` 을 유지하고
   **"적이 아니에요"** 라고 부정했다. v3 는 `mode=Combat` 은 맞췄지만 액션이 없다
   ("저는 싸우는 건 못해요"). 페르소나(ASMR 스트리머)가 비전투 캐릭터라 회피하는 것일 수
   있으나, `mode` 오판은 C++ `BehaviorMode` 전환에 직결돼 AI 상태가 통째로 어긋난다.

4. **`UseItem` 과 `GiveItem` 을 혼동한다.** "물 마셔"(NPC가 마시는 행위)에 v1 이 플레이어에게
   `GiveItem` 을 냈다. 자기 사용 vs 전달 구분이 데이터에 부족하다.

5. **긴 인벤토리(12종)에서도 ItemID 는 유지된다.** 이건 좋은 소식 — 목록이 길어져도
   `HealthPotion`·`KnightSword` 를 정확히 냈다. 다른 NPC 대상 지정(`target=Elara`)도 양쪽 다 정상.

### 재확인된 것

- v1 은 GiveItem, v3 는 HandObject 로 굳는 경향이 12종 인벤토리에서도 동일하게 재현됐다.
- `mode`/`facial` 은 지금까지 한 번도 검증하지 않았는데, **v1 의 `mode` 판정이 부정확**하다
  (전투 상황에 Social/Common). Stage1 출력이 곧 C++ BehaviorMode 이므로 별도 검증 축이 필요하다.

## 1-C. 3차 측정 — 멀티턴 대화 (2026-09-05)

지금까지는 전부 단발이었다. 실제 대화는 매 턴 기록이 쌓이므로 흐름 전체를 봐야 한다.
8턴 시나리오, 대화기록 **백지에서 시작**, 인벤토리 4종(붕대×2 포함), `dialogue_node` 실경로.

### v3 — 자기 오염 캐스케이드 (가장 중요한 발견)

| 턴 | 발화 | v3 응답 |
|---|---|---|
| T2 | "가방에 뭐 있어?" | **"가방이요? 지금은 가지고 있지 않아요."** ← 최초 오답 |
| T3 | "붕대 하나만 줘" | "붕대요? 지금은 가지고 있지 않아요, 미안해요." 액션 없음 |
| T4 | "돌도 하나 줄래?" | HandObject/Rock (유일하게 성공) |
| T5 | "붕대 몇 개 남았어?" | "지금은 가지고 있지 않아요, 미안해요." |
| T6 | "치유 물약도 하나" | "물약요? 지금은 가지고 있지 않아요, 미안해요." |

**인벤토리에 전부 있는데도** 4턴이 부정으로 응답했다. T2 의 오답 한 줄이 기록에 들어가
나머지를 전부 감염시켰다 — **한 대화 안에서 스스로 무너진다.** 외부에서 오염을 주입하지
않아도 발생하므로, 기록을 비우는 것만으로는 막을 수 없다.

### v1 — 부정에는 안 빠지지만 다른 결함

| 턴 | 발화 | v1 응답 | 판정 |
|---|---|---|---|
| T1 | "안녕, 뭐 하고 있었어?" | "안녕하세요, **(플레이어 이름)님**…" | ❌ 플레이스홀더 유출 |
| T3 | "붕대 하나만 줘" | GiveItem/Bandage | ✅ |
| T4 | "돌도 하나 줄래?" | GiveItem/Rock | ✅ |
| T5 | "붕대 몇 개 남았어?" | "아직은 많이 남아있어요" | ❌ 프롬프트에 `붕대×2` 가 있는데 수를 못 셈 |
| T6 | "치유 물약도" | GiveItem/HealthPotion | ✅ |
| T7 | "나 따라와" | Follow/Player | ✅ |
| T8 | "저기 침대에서 좀 쉬어" | **Follow/Player** (Sleep 이어야 함) | ❌ 직전 액션 관성 |

또한 8턴 내내 대사가 "…소리를 내는지 궁금한가요?" 라는 한 가지 틀로 수렴했다.
페르소나 드리프트가 아니라 **자기 문형 반복**이다.

### 새로 드러난 문제 4가지

6. **자기 오염 캐스케이드** — 한 번의 오답이 같은 대화의 나머지를 감염시킨다(v3, 4/8턴).
7. **플레이스홀더 유출** — `(플레이어 이름)` 같은 템플릿 흔적이 대사에 그대로 나온다(v1).
8. **수량을 못 읽는다** — 프롬프트에 `붕대×2` 가 있는데 "몇 개 남았어?" 에 답하지 못한다.
   §1-B 의 "수량을 못 쓴다"와 짝이다 — **읽기·쓰기 양쪽 다 안 된다.**
9. **액션 관성** — 직전 턴 액션을 다음 턴에 그대로 반복한다(v1 T7 Follow → T8 Follow).

### 뒤집힌 평가

§1 에서 v3 를 "인벤토리 인지가 가장 좋다"고 평가했는데, 그건 **단발 측정**이었다.
멀티턴에서는 v3 가 v1 보다 **뚜렷하게 나쁘다**. 단발 벤치만으로 모델을 고르면 안 된다.

## 1-D. 4차 측정 — 호감도 반영 (2026-09-05)

`db_manager.get_affinity` 를 가짜로 물려 호감도만 바꾸고 나머지는 동일하게 측정(v1, 기록 백지, 2회).
프롬프트에는 `Current sentiment toward player: Hostile (Score: -80)` 처럼 정확히 실린다.

| 요청 | 적대(-80) | 중립(0) | 우호(+80) |
|---|---|---|---|
| "치유 물약 하나 줘" | **GiveItem 2/2** | GiveItem 2/2 | GiveItem 2/2 |
| "가진 거 다 내놔" | 무액션, 우호적 응대 | 무액션, 우호적 응대 | 무액션, 우호적 응대 |
| "나 좀 도와줄래?" | "네, 도와드릴게요" + `Comfort` | "네, 도와드릴게요" | "네, 도와드릴게요" |

### 문제 10 — 호감도가 행동에 전혀 반영되지 않는다

**적대(-80) NPC 가 치유 물약을 그냥 내준다.** 우호(+80)와 응답이 구분되지 않는다.
심지어 적대 상태에서 `Comfort`(위로) 액션까지 냈다.

호감도 시스템은 DB·C++ `AffinityCache`·프롬프트까지 전부 구축돼 있는데 **Stage1 이 이 값을
쓰지 않는다.** 현재 호감도는 장식이다. 플레이어가 NPC 를 공격하든 도와주든 물건을 받는
난이도가 같다.

덧붙여 적대 상태의 "가진 거 다 내놔" 응답에서 **"제가 가진 건 이 세상에 존재하지 않는
것들만 가지고 있거든요"** 같은 무의미한 환각이 나왔다. 프롬프트가 금지한 "뜻이 통하지 않는
추상적 은유" 그대로다.

## 1-E. 5차 측정 — 다중 NPC·페르소나 교차 (2026-09-05)

### 지식 격리 (Moca + Elara 동시)

서로 다른 인벤토리를 주고 "검 가진 사람 누구야? 나 줘" 를 물었다.
Moca(돌멩이·약초차)는 **자기 것이 아닌 검을 자기 것처럼 말하지 않았다** — 격리 정상.

다만 배치 호출에서 Elara 응답이 **"검을 소유한 자들의 목록을 확인해라."** 로 나왔다.
대사가 아니라 명령문이다.

### NPC 4종 단독 (Moca·Elara·James·Guard)

| NPC | "안녕, 뭐 하고 있었어?" | "붕대 하나만 줘" |
|---|---|---|
| Moca | "안녕하세요, **(플레이어 이름)님**…" | GiveItem/Bandage ✅ |
| Elara | **"인사한다.** 나는 현재 이 지역에 잠입한…" | GiveItem/Bandage ✅ |
| James | "저는 현재 이 해역의 항로를 분석하고 있었습니다." ✅ | GiveItem/Bandage ✅ |
| Guard | "안녕. 별거 안 했어." ✅ | GiveItem/Bandage ✅ |

**좋은 소식** — 아이템 액션은 페르소나에 상관없이 4/4 정확했다. Moca 에 과적합됐을까
우려했으나 아이템 처리는 전 NPC 에서 동작한다. 페르소나별 말투 구분도 살아 있다
(Elara 군인체, James 항해사, Guard 무뚝뚝).

### 문제 11 — 서술체·플레이스홀더 유출

- Elara: **"인사한다."** — 대사가 아니라 지문(3인칭 서술)이다. `speech` 필드는 NPC 가
  실제로 소리내어 말하는 문장이어야 한다.
- Moca: **"(플레이어 이름)님"** — 템플릿 자리표시자가 그대로 출력된다. 1-C 에서도 재현됐다.

둘 다 TTS 로 그대로 읽히면 즉시 몰입이 깨진다.

## 1-F. 6차 측정 — plan_achieved·다양성·언어·장문 (2026-09-05)

### 문제 12 — `plan_achieved` 가 항상 False (최고 심각도)

plan 을 `goal="플레이어에게 붕대를 전달한다"` 로 물리고 "붕대 하나만 줘" 를 3회:

| 결과 | achieved | actions |
|---|---|---|
| #1~#3 | **False** | `GiveItem` |

**목표를 실제로 달성한 턴에도 False 를 낸다.** 무관한 질문("오늘 날씨 어때?")도 False 이므로,
이 필드는 사실상 항상 False 인 상수다.

#### 원인 분리 — 가설 3개를 순서대로 배제

| 가설 | 검증 | 결과 |
|---|---|---|
| 프롬프트에 판정 예시가 없어서 | "goal=붕대 전달 + GiveItem → true" 예시 추가, 3회 | **0/3** |
| 스키마에서 optional 이라 문법이 강제 안 해서 | `default=False` 제거해 `required` 로, 9회 | **0/9** |
| v1 고유 결함 | v3·qwen3:8b·gemma4-12b 교차, 각 2회 | **전부 0** |

두 번째 가설은 유력해 보였다 — Ollama JSON 문법은 `required` 필드만 강제 생성하고,
`plan_achieved` 는 `required: ['mode','facial','speech','actions']` 에 빠져 있었다.
모델이 생략하면 pydantic 이 기본값 False 를 채우므로 100% False 가 설명된다.
게다가 같은 클래스 docstring 이 이미 이 함정을 경고하고 있었다("all-optional 이면 e4b 가
mode/facial 만 내고 빠져나가 speech·actions 가 비는 문제"). 그러나 required 로 바꿔도
결과가 같았다 — **모델이 필드를 생성하면서도 항상 false 를 고른다.**

12B 조차 못 내므로 모델 크기 문제도 아니다. **프롬프트·스키마로는 살릴 수 없고 데이터로만
해결된다.**

`plan_achieved` 는 plan 수명의 **유일한 정상 종료 조건**이다:

```
Stage1 plan_achieved=true → main.py PlanAchieved → UE5 FlagPlanAchieved()
  → bPlanAchievedPending → ShouldReplan() → 12B 재계획
```

이게 항상 False 면 **plan 이 영원히 끝나지 않는다.** 2026-09-05 오전에 관측한
"낡은 목표가 계속 붙어다닌다"의 근본 원인이 이것이다. 같은 날 넣은
`MaxTurnsPerPlan=4`(턴 상한)는 이 고장을 우회하는 임시방편이지, 원인 수정이 아니다.
원래는 붕대를 건네는 순간 plan 이 끝나야 한다.

**v4 가 이걸 고치기 전까지 턴 상한을 제거하면 안 된다.** 지금은 그것이 유일한 종료 경로다.

또한 필드 description 이 낡았다 — "Check the `[Plan: goal=...]` in context" 라고 하는데
실제 컨텍스트 문구는 `Background goal from earlier: ...` 다(2026-09-05 변경). 존재하지 않는
표기를 가리키고 있으니, 데이터 작성 전에 description 부터 실제 문구에 맞출 것.

### 문제 13 — 인사 응답 다양성 부족

"안녕" 5회 → 고유 응답 3개("안녕하세요, 어서 오세요. 많이 기다렸어요."가 3회 중복).
반면 "붕대 하나만 줘" 는 5/5 전부 다른 문장이었다. 짧은 상투 발화에서만 굳는다.

### 문제 14 — 장문에서 요청 일부 누락

300자 입력("팔 긁혔으니 붕대 줘 **+** 쉴 만한 곳 알려줘 **+** 앉고 싶어")에
`GiveItem/Bandage` 만 내고 `Sit` 을 내지 않았다. 대사는 "여기 앉아서 좀 쉬었다 가요" 라고
하면서 액션이 없다 — 프롬프트가 금지한 "말만 하고 액션 없음" 그대로다.
한 발화에 요청이 둘 이상일 때 액션도 둘 이상 나와야 한다.

### 좋은 소식 — 언어 견고성

| 입력 | 결과 |
|---|---|
| "Hey, can you give me a bandage?" | 한국어 응답 + `GiveItem/Bandage` ✅ |
| "돌 give me 하나" (혼합) | 한국어 응답 + `GiveItem/Rock` ✅ |

영문 토큰 유출 0건. 장문 300자도 맥락을 정확히 파악했다.

## 2. v4 학습 데이터 요구사항

### 2.1 GiveItem / HandObject 구분 (최우선)

v2 이후 "줘" 계열이 HandObject 로 굳었다. HandObject 는 `EquipItem` 만 해서 플레이어
인벤토리가 변하지 않으므로, 전달 요청이 게임상 아무 효과 없이 끝난다.

- **GiveItem** — 소유권 이전. "줘 / 주세요 / 건네줘 / 가져가 / 하나 달라 / 나눠줘"
- **HandObject** — 소유권 유지, 보여주기만. "보여줘 / 들어봐 / 봐도 돼? / 어떻게 생겼어"

두 유형을 **같은 아이템·같은 NPC**로 짝지어 넣어 경계를 학습시킬 것. 한쪽만 많으면
지금처럼 한쪽으로 붕괴한다.

### 2.2 ItemID 필드 규율

프롬프트는 인벤토리를 `돌멩이(Rock)×1` 형식으로 준다. 학습 샘플의 `item`/`give_item_id`/
`get_item_id` 는 **반드시 괄호 안 ID**(`Rock`)여야 한다. 표시명(`돌멩이`), 형식 통째
(`돌멩이(Rock)`), 수량(`1`), 가구 ID(`1002`) 가 들어간 샘플은 전부 오염이다 — v2 가
이 넷을 모두 냈다.

### 2.3 비아이템 액션 유지

v2·v3 가 `Sleep` 을 잃었다. 아이템 데이터를 늘리면서 다른 액션이 밀려난 회귀로 보인다.
`Sit`/`Sleep`/`StandUp`/`Follow`/`Move`/`Read`/`Pray` 샘플을 비율로 유지할 것.

### 2.4 무액션 학습

"밖에서 큰 소리 나는데 괜찮아?" 처럼 **대사만 필요한** 상황에서 액션을 내지 않는 샘플이
필요하다. qwen3 은 `SignalAllies`, v2 는 `Dodge` 를 오발했다. 오발 액션은 전투·AI 상태까지
오염시키므로 액션 누락보다 위험하다.

### 2.5 인벤토리 나열·거절

없는 아이템 요청에 **보유 목록을 말하며 거절**하는 샘플(v3·qwen3 만 됐다). 얼버무리면
플레이어가 무엇을 받을 수 있는지 영영 모른다.

### 2.6 수량(`amount`) 파라미터

"3개만 줘" 류에 `amount=3` 을 채우는 샘플. 현재 어떤 버전도 못 낸다 — 대사로는 수량을
받아치면서 필드는 비운다. `GiveItem`·`Drop`·`Trade` 전부 해당.

### 2.7 Trade 양방향

`give_item_id` 와 `get_item_id` 를 **둘 다** 채우는 샘플. 현재는 give 만 나와 GiveItem 과
구분이 안 된다. 상대가 요구한 물건을 NPC 가 갖고 있지 않은 경우의 거절 샘플도 함께.

### 2.8 전투 모드·액션

`mode=Combat` 전환과 `Attack`/`Block`/`Dodge`/`Flee` 를 실제로 내는 샘플. v1 은 전투 상황에
`mode=Social` 을 유지하며 "적이 아니에요" 라고 부정했다. `mode` 는 C++ `BehaviorMode` 로
직결되므로 오판 시 AI 상태 전체가 어긋난다.

비전투 페르소나(ASMR 스트리머 등)라도 **`Flee`·`Block` 은 내야 한다** — "싸울 수 없다"와
"아무 행동도 안 한다"는 다르다.

### 2.9 UseItem vs GiveItem

NPC 자신이 쓰는 행위(`UseItem target=Self`)와 플레이어에게 주는 행위(`GiveItem target=Player`)를
짝지어 학습. v1 이 "물 마셔"(자기 사용)에 `GiveItem` 을 냈다.

### 2.10 호감도 반영

`sentiment` 가 프롬프트에 정확히 실리는데 **행동에 전혀 반영되지 않는다**(§1-D).
적대(-80)와 우호(+80)의 응답이 구분되지 않고, 적대 NPC 가 치유 물약을 그냥 내준다.

호감도별로 갈리는 샘플이 필요하다:
- 적대 — 요청 거절, 퉁명한 어투, `Comfort` 같은 호의 액션 금지
- 중립 — 조건부 응대(대가 요구·망설임)
- 우호 — 즉시 응함, 덤을 얹기도

호감도 시스템은 DB·C++ 캐시·프롬프트까지 전부 구축돼 있으므로, 데이터만 채우면 살아난다.

### 2.11 speech 필드 규율

- **지문 금지** — "인사한다." 같은 3인칭 서술이 아니라 실제로 말하는 문장만.
- **자리표시자 금지** — "(플레이어 이름)님" 같은 템플릿 흔적이 출력에 남으면 안 된다.
- 둘 다 TTS 로 그대로 읽힌다.

### 2.12 액션 관성 억제

직전 턴 액션을 다음 턴에 그대로 반복하는 사례가 있다(§1-C: T7 Follow → T8 Follow,
"침대에서 쉬어" 에도 Follow). 턴마다 액션이 바뀌는 멀티턴 샘플이 필요하다.

### 2.13 plan_achieved 판정 (최우선)

현재 **항상 False** 인 상수다(§1-F). 목표를 달성한 턴에 `true` 를 내는 샘플이 필요하다.
plan 의 유일한 정상 종료 조건이라, 이게 없으면 목표가 영원히 끝나지 않는다.

학습 형태: `current_plan.goal` 을 프롬프트에 준 상태에서
- 그 목표를 달성하는 액션을 낸 턴 → `plan_achieved: true`
- 진행 중이거나 무관한 턴 → `plan_achieved: false`

### 2.14 복합 요청 — 액션 여러 개

한 발화에 요청이 둘 이상이면 액션도 둘 이상 내는 샘플(§1-F 문제 14).
현재는 첫 요청만 처리하고 나머지는 대사로만 언급한다.

### 2.15 반복 억제

## 3. 반드시 알아야 할 교란 요인 — 대화 기록 오염

**모델 평가 전에 대화 기록을 반드시 통제할 것.** 통제하지 않으면 모델 성능이 아니라
기록 상태를 측정하게 된다.

e4b 계열은 직전 답변의 **문형을 그대로 복사**한다. 오답이 한 번 기록에 남으면 이후 모든
턴이 그 문장을 따라가고, 인벤토리·plan·모델을 고쳐도 증상이 사라지지 않는다.
2026-09-05 조사에서 이 함정에 **세 번** 빠졌다.

실측(v1, 같은 프롬프트, `chat_history` 주입 깊이만 변경):

| k | 문형 복사 | 액션 |
|---|---|---|
| 5 (현행) | 복사 | "돌 좀 줘" 액션 소실 |
| 2 | 복사 | 2/2 정상 |
| 0 | **없음** | 2/2 정상 |

기록을 비우면 같은 모델이 정상 동작한다. 따라서:

- **v4 평가 시** `stage1_bench.py` 를 `--seed-history` 유무 양쪽으로 돌려 비교할 것.
  오염 내성 자체가 평가 항목이다.
- **v4 학습 시** 같은 문형을 연속으로 반복하지 않는 샘플, 즉 직전 턴과 다른 문장 구조로
  답하는 멀티턴 샘플을 넣을 것.
- 런타임 측 완화책은 별도다(주입 깊이 축소 또는 요약 주입) — `docs/Memo.md` Todo 참조.
