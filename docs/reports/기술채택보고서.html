A. 시스템 아키텍처 (2개 항목)
#01 Remote Cortex
UE5(Body) + Python(Brain)
W03~현재 불변 		LLM·RAG·TTS·ASR 연산을 언리얼 엔진 내부에서 돌리면 VR 90Hz 프레임이 깨지고, 방대한 Python ML 생태계를 C++에서 직접 활용 불가. UE5는 렌더링·물리·결정론 실행만 담당하고, Python 서버 3개(:8000 인지 / :8001 TTS / :8002 ASR)가 추론을 전담하는 Remote Cortex 패턴 정립. 프로세스 간 네트워크 왕복 지연 발생, 서버 3개+Ollama 운영 복잡도, 두 프로세스에 분산된 상태 동기화 관리 부담. • UE5 내장 추론(NNE/ONNX)
• 클라우드 API 직접 호출
• gRPC / HTTP REST 		Python ML 스택을 그대로 쓰면서 엔진은 순수 실행만 남기는 유일한 경로. 지연 문제는 3계층 분담으로 흡수.
#02 3계층 두뇌 모델
대뇌(LLM)·소뇌(SLM)·척수(C++)
Warm 1.1s / 0ms 		LLM 호출 1회가 초 단위인데 NPC는 피격·위협에 즉시 반응해야 함. 전부 LLM이면 '전투 턴에 금붕어'가 되고, 전부 C++면 자율성이 상실됨. 역할 3분할:
• 대뇌: 플래너 qwen3:8b (전략, 초 단위)
• 소뇌: 파인튜닝 e4b (즉응 hot loop)
• 척수: C++ 반사 테이블·전투 셀렉터 (0ms) 		층 간 정합성 유지 비용 발생, 소뇌 Reflex가 척수 테이블로 이동하는 등 경계 변동, 상태 소유권 충돌 위험. • 단일 LLM 긴 컨텍스트
• Utility AI / GOAP 순수 C++
• 행동 정책 캐시 		"매 틱 AI를 부르면 컴퓨터가 터진다"는 현실적 출발점. 실측 e4b warm 1.1s vs 12B cold 11s로 계층 분담 필요성 확정.
B. 인지 엔진 (Python) (4개 항목)
#04 FastAPI + LangGraph
선형 파이프라인 멀티 에이전트
Linear Pipeline 		발화 하나에 맥락 해석 → 대사 생성 → 구조화 액션 추출 → 규칙 검증이 순차 필요하고 검증 실패 시 재시도해야 함. 단일 프롬프트는 4B가 감당 불가. LangGraph 노드로 선형화:
Input → Supervisor → Dialogue → Output → Rules.
Rules 거부 시 Supervisor를 거쳐 대사만 1회 재시도. 		노드 하나가 예외로 죽으면 전체 빈 배치 폴백(cp949 크래시 사례), LangChain 래퍼 오버헤드 존재, 노드 간 암묵적 상태 계약. • 순수 asyncio 함수 체인
• AutoGen / CrewAI
• 단일 대형 프롬프트 		이론 청사진을 그래프로 직접 이식 가능. 노드별 모델 교체(Stage1=e4b, Stage2=8B)와 조건부 재시도가 프레임워크 수준에서 해결.
#05 Pydantic v2 Rules
Zero-LLM 결정론적 규칙 검증
0ms 무비용 		LLM 출력이 자유분방하여 데미지 9999, NaN 좌표, 없는 타겟(Strategic Position), 죽은 적 오버킬 등이 발생. Rules 역할을 LLM에서 순수 Pydantic v2 코드로 강등.
• 데미지/속도 수치 클램핑 (MAX_DAMAGE=100)
• 런타임 valid_targets 화이트리스트 대조
• target enum grammar 강제 		새 액션마다 수작업 규칙 작성 필요, 정적 목록이 런타임과 어긋나면 실존 NPC 액션이 조용히 증발(Skadi/Moca 버그). • LLM Rules 에이전트 (원안)
• JSON Schema만 검증
• UE5 C++ 단에서만 검증 		검증은 결정론적이어야 하고 지연시간이 0ms여야 함. Pydantic v2 strict 모드가 무비용으로 강력한 게임 무결성 제공.
#06 Ollama 2-Stage 라우팅
로컬 LLM + 계획 캐싱
Hot 1.1s / Cold 1.5s 		NPC N개가 매 턴 LLM 호출. 클라우드는 비용/지연 누적, 로컬은 VRAM 16GB 한도 내 LLM+TTS+ASR+PIE를 감당해야 함. 큰 모델은 느리고 작은 모델은 액션 누락. 로컬 Ollama 단일화.
• Stage 1: 파인튜닝 e4b (hot loop, 매 턴 대사+액션)
• Stage 2: 플래너 qwen3:8b (replan 시만)
계획 캐싱("비싸게 1회, 싸게 N회") 및 선제 웜업(342ms). 		VRAM 16GB가 모든 결정을 지배(CosyVoice2 롤백, ASR CPU 전환), 계획 캐싱 시 낡은 플랜 고집 위험, thinking 토큰 함정. • 클라우드 API (제거됨)
• vLLM 직접 서빙
• 단일 대형 모델 (26B 17GB 초과) 		처음부터 로컬 고수. e4b warm 1.1s vs 12B 11s 실측이 2-Stage 및 계획 캐싱 절충안의 직접적 근거.
#08 FAISS + MiniLM RAG
NPC별 지식 격리 벡터 기억
누출 0건 실측 		NPC별 lore·페르소나·이력을 매 프롬프트에 넣으면 4B 컨텍스트(2048) 초과. NPC A만 아는 비밀을 B가 발화하는 지식 누출 방지 필요. NPC별 독립 FAISS 벡터스토어 구축(lore/persona/history/*.md). all-MiniLM-L6-v2 CPU 임베딩. 실측 결과 타 NPC 지식 누출 0건 확인. MiniLM 영어 중심성, 지식 마크다운 수작업 관리, 대화 요약 프롬프트 영어 오염 위험(한글화로 보정). • Chroma / Qdrant 서버형 DB

D. NPC AI (UE5 C++) (4개 항목)
#12 StateTree 전환
BT에서 StateTree 마이그레이션
BT 완전 제거 		LLM이 액션 큐를 채우는 구조에서 BehaviorTree는 사실상 '큐에 뭐 있나→실행' 2개 노드뿐인데 BTTask 클래스와 완료 경로만 난립함. MCPStateTreeAIComponent + STTask_PrepareNextAction(Dequeue) + STTask_ExecuteSmartAction(실행) 전면 교체. BB 전용 키 4개 제거. 에디터 수작업(Transition 바인딩) 필수, StateTree 신규 기능으로 참고 자료 부족, 마이그레이션 과도기 데드코드 관리. • BehaviorTree 유지
• 순수 C++ 상태머신
• Utility AI 플러그인 		결정은 LLM 큐가 하고 UE5는 실행만 전담하는 모델에서, StateTree의 상태+태스크+InstanceData가 큐 소비에 가장 부합.
#14 EQS + LLM 전술 위치
request_gen 전술 위치 결정
EQS 2에셋 고정 		어디로 이동할지 LLM에게 3D 좌표 배열을 던지는 것은 극히 비효율적. 순수 EQS만 쓰면 성격(공격적/신중)이 위치 선택에 반영되지 않음. 좌표 탐색은 UE5 EQS가 전담, LLM은 SAFE / OPTIMAL / AGGRESSIVE 3후보 중 택일만 수행. request_gen 카운터로 stale 응답 차단. EQS 에셋 2개 고정. Named Parameter가 Test Score Factor에만 바인딩 가능, LLM 왕복으로 수백 ms 소요(raw 호출 400ms 단축), gen 규칙 위반 시 고착 위험. • LLM에 좌표 직접 전달
• 순수 EQS 스코어링
• NavMesh 랜덤 이동 		"좌표 계산은 EQS, 선택은 LLM" 분담 확립. EQS 에셋 난립을 막고 파라미터로 대응하는 단일 표준 정립.
#15 AIPerception 배치 전송
EmergencyReport 시간창 배치
0.2~0.5s 배치 		NPC 시야·청각·피격 이벤트를 발생할 때마다 매번 Python에 전송하면 네트워크 트래픽 폭주 및 LLM 큐 과부하 발생. NPCStateComponent가 0.2~0.5초 시간창 동안 이벤트를 모아 NPC별 1회 emergency_report로 배치 전송. 피격 LastHitTime 2초 가드, 시청각은 변화 시만 전송. 배치 시간창만큼 반응 지연(0.3s) 발생(척수반사가 0ms로 보완), C++ 기본값이 BP CDO에 덮여 튜닝 혼선 발생. • 매 이벤트 즉시 전송
• 5초 주기 전체 스냅샷
• Python 측 주기적 폴링 		이벤트 주도 방식과 시간창 배치의 결합이 네트워크 트래픽 방어와 반응성 사이의 최적 절충점.
#16 C++ 척수반사 테이블
SLM Reflex 대체 C++ 반사
0ms 결정론 		피격·위협 시 330ms의 SLM Reflex(소뇌)조차 VR 피격 반응으로는 느리고, VRAM 점유 및 출력도 몇 가지로 고정 수렴함. C++ FReflexRule 테이블 + TryReflexReact()로 자극→액션 큐 주입을 0ms 결정론으로 처리. Python report는 단순 통보/기록 전용 전환. 반사 규칙이 C++ 코드 테이블이라 페르소나별 다양성은 스탯 가중치에 의존, LLM이 반사 발생을 즉시 모르면 재계획 지연. • SLM Reflex 유지 (330ms)
• e2b 초경량 모델
• BT/ST 조건 노드 		반사 동작의 출력 공간은 한정적이므로 C++ 척수로 내리는 것이 자연스럽고 VRAM 1.8GB 절약. 0ms 반응 달성.

#21 물리 기반 전투
운동에너지 + 부위 + 액티브 래그돌
½mv² 공식 		히트스캔 즉발 공격은 VR 타격감이 전무. 손을 휘두르는 속도, 맞은 부위, 쓰러지는 물리 반응이 유기적으로 연결되어야 함. ½mv² 손 속도 델타 기반 운동에너지 데미지(밀치기/강타 2단 임계). BoneToBodyPart 부위별 배율(머리 2.0/사지 0.75). 약타 Flinch / 강타 넉다운 액티브 래그돌. Physics Asset 및 기상 몽타주 에셋 필수, 손 속도 트래킹 튐 클램핑 필요, VR 실기 PIE 튜닝 난이도. • 히트스캔 + 고정 피격 애니메이션
• Chaos Physics 전면 래그돌
• 마켓플레이스 플러그인 		기존 TakeDamage 경로에 FPointDamageEvent만 얹어 기존 시스템 파괴 없이 부위 피격과 물리 래그돌을 결합.
