# A. 시스템 아키텍처

## 1. Remote Cortex — UE5(Body) + Python(Brain) 분리

**① 문제**
NPC가 LLM으로 자율 행동하려면 LLM 추론·RAG·TTS·ASR 같은 연산 집약 작업이 필요한데, 이를 게임 엔진 프로세스 안에서 돌리면 렌더링·VR 프레임(90Hz)이 깨진다. 또한 Python ML 생태계(LangGraph·torch·faster-whisper)를 UE5 C++ 안에서 직접 쓸 수 없다.

**② 해결**
UE5는 렌더링·VR 상호작용·물리·결정론 실행만, Python 서버 3개(CognitiveEngine :8000 / TTSService :8001 / ASRService :8002)가 추론을 전담. 첫 주(W03, `0a8193b`)부터 "FastAPI 서버 + UE5 WebSocket 클라이언트" 골격으로 시작했고 이후 한 번도 바뀌지 않았다(결정원장 §G).

**③ 단점**
- 프로세스 경계를 넘는 매 요청이 직렬화·네트워크 왕복을 수반 — 지연이 곧 몰입도 문제(W06 *"LLM이 구동하는 동안 시간이 걸리니까 그 사이에 보여줄 게 필요함"*).
- 서버 3개 + Ollama + 에디터를 함께 띄워야 해 운영 복잡(`Server.bat`·`Dev.bat`로 완화).
- 상태가 두 프로세스에 분산 — Python이 UE5 NPCMap 상태를 모른 채 임의 폴백하던 사고(W20 TTS dispatch 하드코딩 폴백 제거).

**④ 대안**
- UE5 내장 추론(NNE 플러그인·ONNX Runtime) — Python 생태계 포기, LLM급 모델 서빙 불가.
- 클라우드 API 직접 호출 — 별도 서버 없이 UE5 HTTP만으로 가능하나 §6 로컬 LLM 결정과 충돌.
- gRPC/HTTP REST — §3 참조.

**⑤ 채택 이유**
Python ML 스택을 그대로 쓰면서 엔진은 결정론 실행만 남기는 것이 W03 연구 목표 6항목("MCP로 4개 LLM 역할 분리 오케스트레이션", "LLM 출력↔Blackboard↔BT 매끄러운 액션")의 유일한 실현 경로였다. 지연 문제는 아키텍처를 바꾸는 대신 §2·§6·§16의 계층 분담으로 흡수했다.

## 2. 3계층 두뇌 모델 — 대뇌(LLM)·소뇌(SLM)·척수(C++)

**① 문제**
LLM 한 번 호출이 초 단위인데 NPC는 피격·위협 감지에 즉시 반응해야 한다. 모든 판단을 LLM에 맡기면 "전투 턴에 그냥 금붕어"(W07 Notion 일기)가 된다. 반대로 전부 C++로 짜면 자율성이 사라진다.

**② 해결**
W05(2026-02-03 "중간정리")에서 확립한 메타포. 대뇌=LLM(전략·서사, 초 단위) / 소뇌=SLM(즉응, 100ms 목표) / 척수=C++(0ms, 결정론). 이후 모든 작업이 "이건 어느 층인가"로 판단됐다(결정원장 §G). 현행 구현: 대뇌=Stage2 플래너(qwen3:8b)+Stage1 e4b, 소뇌=Stage1 파인튜닝 e4b(hot loop), 척수=`TryReflexReact` 반사 테이블·전투 셀렉터·DiceSystem.

**③ 단점**
- 층 사이 정합성 유지 비용 — 반사가 일어난 걸 LLM이 모르면 다음 replan이 한 박자 늦은 지시를 낸다(W34 `reflex_action` 메모리 기록으로 보완).
- 층 경계가 시간이 지나며 이동 — SLM Reflex(소뇌)가 W34에 C++ 테이블(척수)로 내려갔다(§16).
- 3층이 각각 상태를 가지면 소유권 충돌 — CLAUDE.md §8 "NPC 상태 소유권" 표가 생긴 이유.

**④ 대안**
- 단일 LLM + 긴 컨텍스트로 모든 판단 — 지연 불가.
- Utility AI/GOAP 순수 C++ — 자율 대화·서사 불가.
- 행동 정책 캐시(`PolicyCacheComponent`, W05 원안) — SLM Reflex·계획 캐싱으로 대체됨(결정원장 §2 역전).

**⑤ 채택 이유**
W03 Notion 일기의 *"매 순간 AI에 요청하면 로컬로 돌려서 컴퓨터가 터질 수 있기 때문"* — 로컬 SLM 결정과 동시에 "LLM을 매 틱 부르지 않는다"가 출발점이었고, 그 자연스러운 귀결이 계층 분담이었다. 실측으로도 유효: e4b warm 1.1s, 12B cold 11s(W34) — 이걸 매 틱 부를 수 없다는 게 숫자로 확인됐다.

## 3. WebSocket + MessageEnvelope 단일 채널

**① 문제**
UE5→Python 요청뿐 아니라 Python→UE5 푸시(ActionBatch·NpcAudioResponse·plan 회신)가 필요하고, NPC N개가 동시에 emergency_report·prompt를 보낸다. 요청-응답 순서도 보장되지 않는다(LLM 응답이 EQS 응답보다 늦게 올 수 있음).

**② 해결**
- 양방향 지속 연결: UE5 `WebSockets` 모듈 + FastAPI WS(W04 `2293735`).
- 모든 메시지를 `MessageEnvelope{msg_id, auth_token, timestamp, type, payload}`로 래핑(W09 `3fd2dc8`, W17 `protocol_version` 추가). Notion 일기(W09)에서 "원격 블랙보드"로 개념화.
- 채널은 `/ws/llm` **하나**. 구 `/ws/slm` 제거, Python이 타입 보고 내부 라우팅(W22, CLAUDE.md).
- 응답 순서 비의존: prompt=`msg_id`, location_decision=`request_gen`으로 수신 측 매칭. 메시지별 `create_task` 동시 처리 + `_ws_send_lock` 송신 직렬화(W24 `398fae0`).

**③ 단점**
- 단일 소켓이라 끊기면 전부 끊김 — W22 "NPC 미이동" 디버깅 결론 ① `/ws/llm` 플래핑.
- 타입 추가 시 UE `EnvelopeBuilder` + Python `EEnvelopeType` + 수신 분기 3곳을 동시 수정 안 하면 **무음 무시**(CLAUDE.md §5, `/add-envelope` 스킬로 강제).
- 콜백 안 mutation·WS 누수 같은 동시성 버그 다수(W17 Critical `00a15e0`, W20 `40461bb`, W29 `b368dc6`).

**④ 대안**
- HTTP REST 폴링 — 서버 푸시 불가, NPC N개 폴링 트래픽.
- gRPC 스트리밍 — UE5 측 플러그인 부재(엔진 내장 아님), 프로토콜 버퍼 툴체인 추가.
- UDP/커스텀 소켓 — 신뢰성·순서 직접 구현.
- 채널 분리(`/ws/llm` + `/ws/slm`) — 초기에 실제로 이랬다가 W22에 단일화.

**⑤ 채택 이유**
UE5 `WebSockets` 모듈이 엔진 내장이라 플러그인 0개로 양방향 푸시가 되고, FastAPI가 WS를 1급으로 지원한다. Envelope 래핑은 "NPC N개 × 타입 M개"를 한 소켓에서 구분하려면 필수였다. 채널 단일화는 UE5 클라이언트 연결 관리를 줄이고 라우팅 책임을 Python 한 곳에 두기 위함.

## 4. FastAPI + LangGraph 멀티 에이전트

**① 문제**
플레이어 발화 하나에 "맥락 해석 → 페르소나 대사 생성 → 구조화 액션 추출 → 규칙 검증"이 순차로 필요하고, 검증 실패 시 되돌아가야 한다. 단일 프롬프트에 다 넣으면 4B 모델이 감당 못 한다.

**② 해결**
W03(2026-01-17) 연구 노트의 4-Agent 청사진(Narrative/Character/Rules/Interface)을 LangGraph 노드로 구현: `Interface_Input → Supervisor → Dialogue → Interface_Output → Rules`, Supervisor 조건 엣지로 라우팅. Rules 거부 시 Supervisor로 1회 재시도(W24 `fc8047b`). 상태는 `AgentState`에 누적 — W09에서 "시공간 메모리" 역할로 채택.

**③ 단점**
- 노드 하나가 예외로 죽으면 전체가 빈 배치 폴백 — W28 cp949 print 크래시가 LangGraph 노드를 통째 죽이던 잠복 버그.
- LangChain 래퍼 오버헤드가 실측으로 확인됨(§7: `with_structured_output` 3506ms vs 직접 1518ms).
- 노드 간 상태 계약이 암묵적 — `raw_response`(단수) 같은 死필드가 남았다(W28 `72c0a25` 삭제).

**④ 대안**
- 순수 asyncio 함수 체인 — 조건 분기·재시도를 직접 짜야 함.
- AutoGen/CrewAI — 에이전트 간 자유 대화 지향, 결정론적 파이프라인엔 과함.
- 단일 프롬프트 — 4B 모델 한계로 액션 누락(W24 `193f554` 실측).

**⑤ 채택 이유**
W03 시점의 이론 골격("MCP로 4개 LLM 역할 컨텍스트 분리 오케스트레이션")을 그대로 그래프로 옮길 수 있었다. 노드별 모델 교체(Dialogue=e4b, Stage2=8B, Interface_Output=e4b)와 조건 엣지 재시도가 프레임워크 기능으로 해결됐다. 래퍼 오버헤드는 핫패스(Stage1)만 §7로 우회했다.

## 5. Pydantic v2 Rules — LLM 없는 규칙 검증

**① 문제**
LLM 출력은 자유분방하다 — 데미지 9999, 좌표 NaN, 존재하지 않는 NPC target("Strategic Position"), 죽은 적 오버킬. W04 Notion 일기: *"AI가 자유분방해서 예외 처리할 게 많아짐"*.

**② 해결**
원래 4-Agent 중 Rules는 LLM 에이전트였으나 W04(2026-01-20)에 *"Rules 역할에 LLM이 필요 없다"*로 판단 전환 → Pydantic v2 코드 검증으로 강등. 4종(수치 클램핑 MAX_DAMAGE=100·상태/조건·자원·논리 정합성). 이후 확장: 필수 파라미터 누락 제거·Mode 보정(W24 `4679a52`), Self/Enemy 센티넬(W24 `0a1c062`), UE5 동봉 `valid_targets` 런타임 화이트리스트(W27 `8143844`, W28 `e9f8fb6`), target enum grammar 강제(W27).

**③ 단점**
- 규칙이 코드라 새 액션마다 수작업 — W04 *"사실상 노가다긴 함"*.
- 정적 화이트리스트가 런타임 NPC와 어긋나면 액션이 **조용히** 사라진다(W28: Skadi/Moca 타겟 액션 증발 버그).
- 검증이 사후 제거 방식이라 LLM이 잘못 낸 액션은 "없던 일"이 될 뿐 재생성은 1회 재시도에 한정.

**④ 대안**
- LLM Rules 에이전트(원안) — 지연 추가·비결정론.
- JSON Schema만으로 검증 — 논리 정합성(자해 거부·거리 조건) 표현 불가.
- UE5 C++ 측에서만 검증 — Python이 먼저 걸러야 UE5까지 잘못된 배치가 안 감.

**⑤ 채택 이유**
검증은 결정론적이어야 하고 지연 0이어야 한다. Pydantic v2 strict 모드가 스키마 검증을 공짜로 주고, 논리 규칙은 코드 몇 줄. W17 Critical/High 픽스 묶음(빈 액션 실행·stale 패킷 등)이 전부 "LLM 자유로움 = 검증 부담"의 연장선이었다.

## 6. Ollama 로컬 LLM + 2-Stage 모델 라우팅 + 계획 캐싱

**① 문제**
NPC N개가 매 턴 LLM을 부른다. 클라우드 API면 비용·지연·의존성이 쌓이고, 로컬이면 VRAM 16GB(RTX 5070 Ti)에 LLM+TTS+ASR+UE5 PIE를 다 넣어야 한다. 큰 모델은 좋지만 느리고(12B cold 11s), 작은 모델은 빠르지만 액션을 빠뜨린다.

**② 해결**

- 계획 캐싱은 낡은 plan 고집 위험 — 원래 N턴 상한, 지금은 이벤트 트리거만.

**④ 대안**

**⑤ 채택 이유**

## 7. Ollama format=schema 구조화 출력 직접 호출

**① 문제**
e4b가 `[Action:]` 태그를 통째로 생략하고 대사만 내는 일이 잦았다(액션 없는 NPC). 구조화 출력이 필요한데 langchain `with_structured_output`은 warm avg 3506ms·분산 1.2~8s(W26 실측).

**② 해결**
W24 `193f554`에서 `with_structured_output(DialogueResponse)`로 액션 누락 해소 → W26 `0f41769`에서 Ollama `/api/chat` `format=<json schema>` 직접 호출 `ollama_structured()`로 교체 — 1518ms(2.3배·안정). 범인은 grammar 디코딩이 아니라 langchain 래퍼였다. `schema_override`로 target enum을 런타임 주입(W27 valid_targets).

**③ 단점**
- 함정 2개 실측(W24): all-optional 스키마면 e4b가 speech·actions를 비움 → required 강제 필요; 텍스트 포맷 프롬프트와 JSON 스키마가 충돌 → `DIALOGUE_STRUCTURED_PROMPT` 분리.
- Ollama Cloud 모델은 format=schema 미지원(마크다운 블록 반환) → `_strip_markdown_json` 우회.
- grammar 강제가 없는 raw 호출에선 bare-string 포맷 깨짐(`"actions":"Sleep"`, W30 eval).
- 자유텍스트(823ms)보다 여전히 2배 느림.

**④ 대안**
- 자유텍스트 + 정규식 파싱 — 빠르지만 액션 누락(원래 상태).
- langchain `with_structured_output` — 2.3배 느림(실측).
- Outlines/guidance 같은 별도 constrained decoding — Ollama 밖 서빙 스택 추가.

**⑤ 채택 이유**
"액션 누락 0"이 게임플레이 필수이고, 지연 2.3배 차이가 실측으로 확정됐다(W26). Ollama가 grammar 강제를 네이티브로 주니 래퍼를 걷어내는 게 가장 짧은 경로였다. 결정원장 §2에 "Stage1 구조화 호출" 역전으로 기록.

## 13. 비동기 액션 완료 모델 + Action Queue

**① 문제**
`STTask_ExecuteSmartAction`이 `ExecuteInteraction` 직후 `OnActionCompleted`를 **동기** 호출해 이동·몽타주 같은 비동기 액션이 즉시 완료 처리 → 큐가 한 프레임에 비워지고 `[Move, Attack]`이 직렬화 안 됨(Attack이 Move를 덮음)(W22).

**② 해결**
- Action Queue 순차 실행은 W07 `33379a8`에서 확립. W08 Facade 분리 시 *"액션 완료 신호 — 이걸 빠뜨리면 큐가 멈춤"* 명시.
- W22 `0428585` 비동기 완료 모델: EnterState는 발행만, `bIsBusy` 폴링 Tick으로 Running 유지. `BaseMove→OnMoveActionCompleted`(도착), `BasePlayActionMedia→OnMontageActionEnded`(몽타주 종료), 즉시형은 switch 말미 자동. `MaxActionDuration` 워치독이 미수신 시 강제 완료. `ClearActiveActionState()`로 리셋 일원화(W22 `95fc71d`).

**③ 단점**
- 새 액션 추가 시 4곳 동시 수정 + 완료 모델 분기 판단 필수(CLAUDE.md §3, `/add-eaction` 스킬로 강제). 빠뜨리면 워치독까지 대기.
- 콜백·워치독 경합 → `bIsBusy` 가드 필요.
- Track/Follow(`MoveToActor` 연속 추적)는 instant 유지 — 예외가 있다.

**④ 대안**
- 동기 완료(원래) — 다중 액션 불가.
- UE5 GameplayAbilitySystem(GAS) — 비동기 어빌리티·태그가 내장. 학습 비용·LLM 큐와의 통합 재설계 필요(개발 기록엔 검토 흔적 없음).
- Latent Action/Task 노드 — BT 시절 방식.

**⑤ 채택 이유**
LLM이 `[Move, Attack, Dialogue]`처럼 배치를 내는데 순차 실행이 안 되면 배치 자체가 무의미. 워치독은 "완료 신호 누락 = 큐 영구 정지"라는 W08부터의 위험을 시스템적으로 막는 안전망.

## 14. EQS + LLM 전술 위치 결정 (request_gen)

**① 문제**
"어디로 이동할까"를 LLM에 좌표 배열로 던지면 비효율(W09 Notion *"그냥 좌표 띡 보내는 거는 에바쎄바"*). LLM은 "기억력이 딸려서 최대한 핵심만 보내야" 한다. 반대로 순수 EQS만 쓰면 성격(공격적/신중)이 위치 선택에 반영 안 된다.

**② 해결**
- W09 6가지 상황 인식 기법 비교(Perplexity vs Gemini) → 인플루언스맵은 UE5 EQS에 위임, Python은 **SAFE/OPTIMAL/AGGRESSIVE 3후보 중 택일만**(W14 `9e96eff`).
- EQS 에셋 7→2 통합(W17 `e87b58a`: `EQS_TacticalPositions`·`EQS_Move`), 신규 에셋 금지, 새 요구는 `UpdateEQSParams()` Named Parameter(W18 `104a9e7`).
- `request_gen` 카운터로 stale 응답 차단(W20) — 후보 ID가 3개 고정이라 신/구 응답을 ID로 구분 못 했음. gen 증가는 `StartTacticalQuery` 한 곳(W22 `95fc71d`), 터미널 상태 금지(W24 Failed 고착 `c1b7eed`).
- LLM 실패·stale도 드랍 안 하고 `_location_decision_fast_path` 폴백 반환 — 안 그러면 UE5 WaitingLLM 타임아웃 고착.

**③ 단점**
- Named Parameter는 Test 노드 Score Factor에만 바인딩 가능, Generator Search Radius는 불가(W18 Memo) — 파라미터화 범위 제한.
- LLM 왕복이 있어 이동 결정에 수백 ms — few-shot raw 호출로 400ms/4토큰까지 줄임(W20).
- gen 규칙 하나 어기면 영구 고착(CLAUDE.md §7) — 실제로 Abort가 gen을 올려 정상 응답을 stale로 만들던 버그(W22).

**④ 대안**
- LLM에 좌표 배열 직접 — 기각(위).
- 순수 EQS 스코어링 — 성격 미반영. 다만 신중/공격 가중치를 EQS 파라미터로 넣는 방향은 W18에서 일부 채택.
- NavMesh 랜덤 + 규칙 — 전술 의미 없음.

**⑤ 채택 이유**
"좌표 계산은 EQS, Python은 선택만"이 W09에 확정된 분담. EQS 2-에셋 정책은 W17 7개 난립 후 정리한 결과로, 이동 요구가 늘 때 에셋이 아니라 파라미터로 대응하게 만든 것.

**④ 대안**

- 5초 주기 전체 스냅샷 — W09 원안("npcmanager 5초 취합")이었으나 실제론 이벤트 배치로 구현.
- Python 측 폴링 — 서버가 UE5 상태를 당길 수 없는 구조.

**⑤ 채택 이유**
W09 Notion 체크리스트 3항목("연타마다 위험 신호 보내면 안 됨" 등)이 그대로 구현됐다. 이벤트 기반 + 배치가 트래픽과 반응성의 절충점.

## 16. C++ 척수반사 테이블 (SLM Reflex 대체)

**① 문제**
피격·위협 시 즉시 반응이 필요하다. W14부터 `emergency_report`(danger ≥ 0.5)를 LangGraph 우회 단일 SLM 호출로 처리(SLM Reflex)했고 W24 raw 전환으로 warm 330ms까지 줄였지만, 여전히 네트워크 왕복 + 모델 호출이고 VRAM을 점유한다. 결과도 Attack/Dodge/Flee 몇 가지로 수렴했다.

**② 해결**
W34 `3868f58`·`9d2f10c`(PR #23): C++ `FReflexRule` 테이블 + `TryReflexReact(Sense, EventType, SourceID, ...)` — 자극→액션 큐 주입·Combat 진입을 0ms 결정론으로. Python `emergency_report`는 **통보 전용**(반사 이력 `reflex_action` 메모리 기록만, `_record_reflex_memory`). 계층 관점에선 소뇌(SLM)가 하던 일이 척수(C++)로 내려간 것.

**③ 단점**
- 반사 규칙이 코드 테이블 — 성격별 다양성은 DiceSystem·스탯 가중치(§17)에 의존.
- LLM이 반사를 모르면 다음 replan이 한 박자 늦음 → 메모리 기록으로 보완했으나 완전하진 않음.
- `CognitiveEngine/README.md`는 아직 "SLM Reflex" 서술이 남아 있음(문서 부채).

**④ 대안**
- SLM Reflex 유지(330ms) — VRAM·지연.
- e2b 초경량 모델 — 여전히 호출 비용.
- BT/ST 서비스 노드로 조건 반응 — 결국 같은 C++ 테이블.

**⑤ 채택 이유**
반사 판단의 출력 공간이 작고(Attack/Dodge/Block/Flee) 결정론이어도 게임플레이가 자연스럽다면 SLM은 과한 비용이다. VRAM 16GB 안에서 e2b 1.8GB를 빼는 효과도 있다(W27 실측). W05 3계층 모델의 "척수=0ms 결정론" 자리에 정확히 맞는다.

## 17. DiceSystem + 전투 셀렉터

**① 문제**
NPC가 명령 수행자처럼 보인다 — 매번 같은 반응. 또 W28에 발견된 **전투 무한공격**: `STTask_PrepareNextAction`이 Combat+TargetActor면 Attack 100% 무한 주입, 전투 종료 경로가 시스템에 없음(플레이어는 Destroy 안 되니 사망·리스폰 후에도 추격).

**② 해결**

- 전투 셀렉터(W28 PR #19): C++ 척수 셀렉터 — 기구현 Attack/Dodge/Block/Flee 재활용, 스탯 파생 가중치(Strength→공격/Agility→회피)+저HP 가중치 급증+주사위. 타겟 사망 종료 게이트(`4c9ee37`), 승리 LLM 통보(`dd48ac1`), `CombatTargetLostTimeout` 8초(`5afe9b4`).

**③ 단점**
- 가중치·임계값 튜닝이 필요(2026-09 `35912e7` "전투 셀렉터 간격 튜닝").
- 성격이 스탯에서만 파생 — 페르소나 텍스트와 별개 축.
- Difficulty를 SLM이 산출한다는 원안(W07)은 기록상 구현 확인 없음.

**④ 대안**
- LLM에 매 전투 턴 문의 — 지연·무한공격은 그대로(LLM 재상담 계기 0이 원인).
- Utility AI 스코어링 — 셀렉터가 사실상 경량 유틸리티 AI.
- 순수 확률 없이 규칙만 — "명령 수행자" 문제 재발.

**⑤ 채택 이유**
W28 인터뷰로 확정: 레퍼토리는 전부 기구현이라 셀렉터만 새로 짜면 됐고, 종료 게이트는 §2 상태 소유권(BB 쓰기는 Controller만) 준수 하에 Controller 핸들러 경유. 같은 날 구현·PIE 검증·머지.

## 18. TTS — OpenVoice v2 + MeloTTS

**① 문제**
NPC 대사를 **한국어·감정 음색**으로, 첫 음 지연(TTFA) < 600ms, VRAM 예산 안에서 합성해야 한다. NPC별 고유 음색이 필요하다.

**② 해결 (5차례 교체 끝에 확정)**
W20~W21 M2 시도 순서: VibeVoice-Realtime-0.5B(표준 transformers API 비호환) → Piper(한국어 미지원, 0샘플) → Coqui XTTS-v2 → **OpenVoice v2 + MeloTTS**(W21 확정: MeloTTS로 KR/EN 기본 발화 → `ToneColorConverter`로 감정별 레퍼런스 음색 zero-shot). W23~26 CosyVoice2(WSL2) 마이그레이션(PR #11) 후 VRAM 과다로 **롤백**(W26 `1d560e8`).
현행: 문장단위 producer↔consumer 스트리밍(W24 `a01aef4`, TTFA 길이 무관 193~329ms), `_synth_lock` 동시 NPC 직렬화(`9410544`), target SE 디스크 캐시, `OV_USE_GPU=0` CPU 합성(`Server.bat`), `[trace=msg_id]` 로그 체인.

**③ 단점**
- 음색 다양성·zero-shot 클로닝 품질은 CosyVoice2보다 낮음(W26 "성능 일부 포기").
- 설치가 pip 한 줄이 아님 — MeloTTS PyPI 빌드 깨져 GitHub `--no-deps` + 전처리 패키지 15개 수동(`requirements.txt` 절차).
- 레퍼런스 WAV를 NPC×감정마다 준비(`voice_map.yaml`, 없으면 6초 자동 생성).
- `sentence-transformers 5.x`가 torchcodec 강제 import → Windows FFmpeg DLL 누락(핀 `<5.0`).

**④ 대안**
- CosyVoice2 — 품질↑, WSL2 필요 + VRAM 2GB(실제 시도 후 롤백).
- XTTS-v2 — 다국어, 라이선스(CPML 비상업)·속도.
- Piper — 빠르지만 한국어 없음.
- 클라우드 TTS(ElevenLabs 등) — 지연·비용·오프라인 불가.
- LLM 토큰 스트리밍 연동 — W24에 "불요(보류)" 판정.

**⑤ 채택 이유**
한국어 지원 + MIT 라이선스 + Windows .venv에서 구동 + CPU 합성으로도 TTFA < 600ms 달성(실측). CosyVoice2는 안정화까지 끝냈지만 "12B 8GB + e4b 3GB + CosyVoice 2GB + PIE" 동시 OOM 압박이 결정적이었다. 결정원장 §2 "TTS 음성모델" 역전 행.

## 19. ASR — faster-whisper

**① 문제**
VR에서 키보드 입력은 불가 — 플레이어 발화를 push-to-talk로 텍스트화해야 한다. 한국어 인식, 단발 요청.

**② 해결**
`faster-whisper`(CTranslate2) 서버(:8002). UE5 `VoiceInputComponent`(AudioCapture)가 s16le PCM을 WS 스트리밍 → `end` 시 일괄 인식. `asyncio.Lock`으로 GPU 직렬화, 버퍼 상한 11.5MB. 코드 기본값은 `large-v3/cuda/float16`이나 운영(`Server.bat`)은 **`small/cpu/int8`**(W26 `beb7d94` VRAM 정리, HF 캐시 4.3GB 삭제).

**③ 단점**
- small 모델은 large-v3 대비 한국어 정확도 하락(개발 기록에 정량 비교 없음).
- 스트리밍 부분 인식 없음 — `end` 후 일괄이라 발화 길이만큼 대기.
- WhisperModel 비-스레드세이프 → 동시 요청 직렬화.

**④ 대안**
- openai-whisper 원본 — CTranslate2 대비 느림·메모리↑.
- Vosk 등 경량 스트리밍 ASR — 한국어 모델 품질.
- 클라우드 STT — 지연·비용.
- UE5 내장 음성 인식 — 없음.

**⑤ 채택 이유**
push-to-talk 단발이라 CPU small(~0.5s)로 충분하다는 판단(W26). VRAM은 LLM에 양보. 모델 크기·디바이스는 env로 되돌릴 수 있게 남김.

## 21. 물리 기반 전투 — 운동에너지 데미지·부위 인지·액티브 래그돌

**① 문제**
히트스캔 즉발 전투는 VR에서 실감이 없다. 손을 휘두르는 속도·맞은 부위·쓰러지는 반응이 물리적으로 이어져야 한다(논문 `VR 실감형 상호작용 시스템.pdf` §3/§4/§5 기반, W26).

**② 해결**
- §4 `½mv²` 데미지: 손 컨트롤러 위치델타/dt로 속도(kinematic이라 `GetVelocity()=0`), 2단 임계(밀치기/강타), 투사체 `AKineticProjectile`. `KineticDamage::Compute/ApplyToNPC` 공용 헬퍼(`6a8e3a9`).
- §5 부위 인지: `BoneToBodyPart` 머리 2.0/사지 0.75, Mixamo·Mannequin 양 네이밍(`bfa4f6e`). 햅틱 B+A 폴백. 패시브 래그돌 + 타격 방향 임펄스.
- §3 액티브 래그돌: 약타 Flinch(상체 PD 복귀)/강타 넉다운→기상, `MaxConcurrentKnockdown` 3, Gemini 5R 반영(PR #13).

**③ 단점**
- Physics Asset·기상 몽타주 등 에셋 전제 — 없으면 `SetSimulatePhysics` 조용히 무효.
- 임펄스 필드가 `FPointDamageEvent`에 없어 데미지를 강도 프록시로 사용.
- 손속도 스파이크(트래킹 튐) 클램프 필요.
- VR 실기 PIE 검증 일부 대기.

**④ 대안**
- 히트스캔 + 애니메이션 hit-react — 실감 없음(교체 사유).
- Chaos Physics 전면 래그돌 — 제어 불가·비용.
- 마켓플레이스 액티브 래그돌 플러그인 — 의존성·커스터마이즈.

**⑤ 채택 이유**
논문 명세가 있었고, 기존 `TakeDamage` 경로에 `FPointDamageEvent`(BoneName·ShotDirection)만 얹으면 부위·래그돌이 결합되는 구조라 침습이 작았다.
